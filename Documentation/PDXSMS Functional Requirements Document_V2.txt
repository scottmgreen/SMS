1. Introduction
1.1 Purpose
This document defines the functional requirements for the PDX Safety Management System (PDXSMS), a software platform designed to support compliance with 14 CFR Part 139 and FAA AC 150/5200-37A. It is intended for developers, analysts, airport safety personnel, and regulatory stakeholders.
1.2 Scope
PDXSMS supports the following capabilities:
* Safety event and incident management
* Risk assessment and mitigation tracking
* Training and competency management
* Audit scheduling and reporting
* Task management and escalation
* Safety performance monitoring
* Role-based access control
* Notification and communication workflows

2. System Context
2.1 Architecture
PDXSMS is implemented using Clean Architecture principles with Domain-Driven Design. It is composed of:
* Domain Layer: Core business logic and entities
* Application Layer: Use cases and services
* Infrastructure Layer: Data access and integrations
* Presentation Layer: RESTful APIs and UI


2.2 Technology Stack
* .NET 8 / C#
* SQL Server
* Mediator (CQRS)



3. Functional Requirements
3.1 Safety Event Management
FR-3.1.1 – Safety Event Creation
ID: FR-3.1.1
Title: Safety Event Creation
Description:
The system shall allow authorized users to create new safety event records with structured documentation, including event type, location, severity, and associated operational context.
Rationale:
Per AC 150/5200-37A §4.2.1 and 14 CFR §139.401(b), airports must establish a system for identifying safety issues and hazards. Documenting safety events is a foundational activity in Safety Risk Management (SRM).
Inputs:
* Event description (validated via Description value object)
* Date/time of occurrence
* Event type (e.g., incursion, excursion, FOD, wildlife strike)
* Location (GeoLocation value object)
* Reporting user credentials
* Initial severity estimate (optional)
Processing:
* Validate input using domain rules
* Assign unique SafetyEventID
* Store event using BaseAuditableEntity pattern
* Trigger notification workflow
* Log event in audit trail
Outputs:
* Confirmation of event creation
* Notification to designated safety personnel
* Audit log entry
Dependencies:
* FR-3.5.1 (User Authentication)
* FR-3.8.1 (Audit Trail)
* FR-3.8.2 (Notification System)


Acceptance Criteria:
* Event created with unique ID and timestamp
* Event types aligned with FAA AC 150/5200-37A examples
* Required fields validated using domain value objects
* Audit trail includes user ID and creation context
* Notification sent to Safety Officer or designated role

FR-3.1.2 – Safety Event Status Tracking
ID: FR-3.1.2
Title: Safety Event Status Tracking
Description:
The system shall support lifecycle tracking of safety events through defined workflow states, including automated transitions and manual overrides.
Rationale:
Tracking the status of safety events supports continuous monitoring and ensures timely resolution, as recommended in AC 150/5200-37A §5.2.2 and §139.402(c)(1).
Inputs:
* SafetyEventID
* New status
* User credentials
* Justification (if manual override)
Processing:
* Validate status transition rules
* Update event record
* Log change in audit trail
* Trigger notifications if required
Outputs:
* Updated event status
* Notification to stakeholders
* Audit log entry
Dependencies:
* FR-3.1.1 (Event Creation)
* FR-3.5.2 (Role-Based Access Control)
* FR-3.8.1 (Audit Trail)


Acceptance Criteria:
* Workflow states: Open ? Investigating ? Under Review ? Closed
* Status changes logged with timestamp and user ID
* Notifications triggered for critical status changes
* Overdue status changes flagged for escalation

ID: FR-3.1.3
Title: Safety Event Response Management
Description:
The system shall enable structured responses to safety events, including assignment of responsible personnel, escalation levels, and mitigation tracking.
Rationale:
Structured response supports proactive risk mitigation and aligns with AC 150/5200-37A §4.2.2.5.5 and §139.402(b).

* Escalation level
* Estimated completion date
Processing:

Outputs:

* Audit log entry
Dependencies:

* FR-3.5.1 (User Management)

Acceptance Criteria:

* Escalation levels: Low, Medium, High, Critical
* Notifications sent based on escalation level
* Timeline tracking with overdue alerts

3.2 Risk Assessment Management
FR-3.2.1 – Risk Assessment Creation
ID: FR-3.2.1
Title: Risk Assessment Creation
Description:
The system shall provide a structured risk assessment capability using a configurable risk matrix (e.g., 5x5) to evaluate hazards associated with safety events or operational changes.
Rationale:
Per AC 150/5200-37A §4.2.2 and 14 CFR §139.402(b)(2), airports must establish a systematic process to analyze hazards and their associated risks. This includes determining severity and likelihood, assigning risk levels, and documenting the results for traceability and mitigation planning.
Inputs:
* Associated SafetyEventID or GeneralIncidentID
* Risk category (e.g., Human Error, Mechanical Failure)
* Severity score (1–5)
* Likelihood score (1–5)
* Risk description
* Mitigation recommendations
* Assessor credentials
Processing:
* Calculate risk score using domain logic: severity × likelihood
* Determine risk level (e.g., Low, Medium, High, Critical)
* Validate input using domain rules
* Store assessment with audit trail and traceability to source event
Outputs:
* Risk assessment record with unique ID
* Calculated risk score and level
* Linked mitigation recommendations
* Audit log entry
Dependencies:
* FR-3.1.1 (Safety Event Creation)
* FR-3.3.1 (Incident Documentation)
* FR-3.8.1 (Audit Trail)
Acceptance Criteria:
* Risk score calculated using domain method CalculateRisk()
* Risk level assigned per airport-defined matrix (e.g., FAA 5x5)
* Assessment linked to originating event or incident
* Mitigation recommendations documented
* Assessor identity and timestamp recorded

FR-3.2.2 – Risk Category Management
ID: FR-3.2.2
Title: Risk Category Management
Description:
The system shall support standardized risk categorization for all assessments to enable classification, filtering, and trend analysis.
Rationale:
Categorizing risks supports trend identification and targeted mitigation strategies, as recommended in AC 150/5200-37A §4.2.1.1.2 and §4.2.2.5.2.
Inputs:
* RiskAssessmentID
* Risk category selection (from domain enum)
* Classification criteria
Processing:
* Validate category against domain enumeration
* Assign category to risk assessment
* Enable filtering and reporting
Outputs:
* Categorized risk assessment
* Enhanced reporting and analytics
Dependencies:
* FR-3.2.1 (Risk Assessment Creation)
* Reporting and analytics modules
Acceptance Criteria:
* Categories include: MechanicalFailure, HumanError, EnvironmentalHazard, Wildlife, Infrastructure, Other
* Category assignment logged with audit trail
* Filtering supported in dashboards and reports
* Historical category data retained for trend analysis

FR-3.2.3 – Risk Mitigation Task Management
ID: FR-3.2.3
Title: Risk Mitigation Task Management
Description:
The system shall support the creation, assignment, and tracking of mitigation tasks linked to risk assessments, with accountability and progress monitoring.
Rationale:
Mitigation is a required step for addressing unacceptable risk, per AC 150/5200-37A §4.2.2.5.5. Task tracking ensures mitigations are implemented, verified, and evaluated for effectiveness.
Inputs:
* RiskAssessmentID
* Task description
* Assigned user
* Due date
* Priority level
* Estimated effort
Processing:
* Create MitigationTask entity with unique ID
* Assign to qualified user
* Track progress through workflow states
* Trigger alerts for overdue tasks
Outputs:
* Task assignment confirmation
* Progress dashboard
* Completion verification
* Accountability reporting
Dependencies:
* FR-3.2.1 (Risk Assessment)
* FR-3.5.1 (User Management)
* FR-3.7.1 (Task Management)
Acceptance Criteria:
* Tasks linked to originating risk assessment
* Workflow states: Pending ? InProgress ? Completed
* Overdue tasks flagged and escalated
* Completion requires sign-off and documentation
* Integration with reporting and compliance dashboards

3.5 User Management
FR-3.5.1 – User Authentication and Session Management
ID: FR-3.5.1
Title: User Authentication and Session Management
Description:
The system shall provide secure user authentication and session management, including support for multi-factor authentication, session timeout policies, and audit logging.
Rationale:
Secure access control ensures that only authorized personnel can perform safety-critical functions. This supports the integrity of the SMS and aligns with AC 150/5200-37A §3.2.2.4 and 14 CFR §139.402(a)(6–7), which require clear lines of safety responsibility and accountability.
Inputs:
* Username and password
* Multi-factor authentication token (if applicable)
* Session parameters (timeout, IP address, device info)
Processing:
* Authenticate user credentials
* Validate role and permissions
* Establish secure session
* Log session activity for audit trail
Outputs:
* Session token
* Authentication confirmation
* Session log entry

Dependencies:
* FR-3.5.2 (Role Management)
* FR-3.8.1 (Audit Trail)
* Security infrastructure (e.g., identity provider)
Acceptance Criteria:
* Supports multi-factor authentication for administrative roles
* Enforces session timeout and renewal policies
* Logs all login attempts, session starts, and terminations
* Integrates with enterprise authentication systems (e.g., AD)
* Session logs include user ID, IP address, and timestamp

FR-3.5.2 – Role-Based Access Control Management
ID: FR-3.5.2
Title: Role-Based Access Control Management
Description:
The system shall support aviation-specific user roles with defined permissions, responsibilities, and hierarchical access control.
Rationale:
Per 14 CFR §139.402(a)(1–5) and AC 150/5200-37A §3.2.2, airports must define and communicate the safety organizational structure, including the Accountable Executive and other SMS roles. Role-based access ensures that users can only access functions appropriate to their responsibilities.
Inputs:
* Role name and description
* Permission matrix
* User-role assignments
* Role expiration date (optional)
* Organizational hierarchy
Processing:
* Create and manage role definitions
* Assign roles to users with temporal tracking
* Enforce access control based on role
* Monitor role expiration and renewal
Outputs:
* Role assignment confirmation
* Access control enforcement
* Audit trail of role changes

Dependencies:
* FR-3.5.1 (User Authentication)
* FR-3.8.1 (Audit Trail)
* Organizational structure definition
Acceptance Criteria:
* Supports roles such as: Accountable Executive, SMS Manager, Safety Officer, Maintenance Manager, Training Manager, Auditor, System Administrator
* Enforces least-privilege access model
* Role assignments logged with timestamp and authorizing user
* Role expiration alerts and renewal workflows
* Supports delegation and hierarchical access control

Not Covered Requirements (Gaps)
From 14 CFR Part 139:
1. §139.325 – Airport Emergency Plan
* Not explicitly addressed in the FRD. Emergency response is partially implied in escalation logic but not mapped to the full EOP requirements (e.g., bomb threats, water rescue, etc.).
2. §139.321 – Handling and Storing Hazardous Substances
* No FRs address fuel farm safety, hazardous materials storage, or fire safety training for fueling personnel.

From AC 150/5200-37A:
1. Chapter 2 – SMS Implementation Plan
* The FRD assumes an implemented system but does not include requirements for SMS Implementation Planning, phasing, or gap analysis documentation.





Partially Covered Requirements
From 14 CFR Part 139:
* §139.303 – Personnel
* Training is covered (FR-3.4.x), but not all required curriculum elements (e.g., radio communication, NOTAMs, etc.) are explicitly listed.
* §139.327 – Self-Inspection Program
* Hazard identification is covered, but daily inspection procedures and equipment requirements are not detailed.
* §139.337 – Wildlife Hazard Management
* Risk categories include “Wildlife,” but no FR addresses wildlife hazard assessments or WHMP integration.

From AC 150/5200-37A:
* §4.3 – Integrated SRM Efforts
* No FR explicitly supports joint SRM panels with tenants or FAA.
* §5.2.3 – Reporting to Accountable Executive
* Dashboards (FR-3.9.1) support this, but no FR mandates reporting cadence or content to the AE.
* §6.2.1.4.5 – Training Material Review
* Training is versioned, but no FR requires periodic review of training content.
* Appendix C – Implementation Checklist
* No FRs support checklist-based implementation tracking or status reporting.
